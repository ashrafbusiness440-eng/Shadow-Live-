# Shadow Live — Reuse-First Engineering Standard
**الحالة:** قاعدة معمارية عامة معتمدة — تسري على كل نظام جديد وكل إصلاح أو إعادة هيكلة (Flutter، Cloudflare Workers، Firestore، R2، Shadow Control، الاختبارات).

## القاعدة الرئيسية
**كل عمل جديد يبدأ بالتحقق من إمكانية إعادة استخدام ما هو موجود، ويُصمَّم بحيث يمكن إعادة استعمال الجزء المشترك منه في أنظمة أخرى عندما تكون الحاجة حقيقية.**
الهدف هو **إعادة استخدام المنطق الموثوق** وليس ربط أنظمة مستقلة ببعضها بالقوة أو بناء طبقات عامة لا تحتاجها المنظومة.

> Reuse first; extract genuine shared behavior; keep domain policy and authorization isolated; prove correctness in every consumer.

## إجراء إلزامي لكل مهمة / PR

1. **فحص موجّه قبل التنفيذ:** راجع الملفات/الخدمات ذات الصلة فقط للعثور على سلوك مماثل أو مكوّن مشترك جاهز. لا تستخدم scans شاملة أو طلبات كثيرة.
2. **قرار إعادة الاستخدام:** 
   - موجود ومناسب: استخدمه بدل نسخه.
   - سلوك مكرر فعليًا في مستهلكين أو أكثر: استخرجه في وحدة صغيرة واضحة ذات واجهة مستقرة، مع اختبارات مخصّصة لها واختبارات تكامل للمستهلكين.
   - خاص بمجال واحد أو التشابه شكلي فقط: اتركه داخل المجال، وحدد سبب عدم مشاركته. لا تُجرّد بشكل مبكر لمجرد احتمال استعمال مستقبلي.
3. **فصل الطبقات:** السلوك التقني المشترك (تحقق المدخلات، pagination، audit primitives، adapters، errors، lifecycle utilities) قابل للمشاركة إذا كانت ضماناته متماثلة. قرارات المال، الصلاحيات، الاعتراضات، الحذف، الملكية، وحفظ الأدلة تبقى لدى المجال المسؤول، حتى لو استخدمت أدوات مشتركة تحتها.
4. **عقد واضح:** ضع الوحدة المشتركة بمكان معروف، API صغيرة، أسماء غير مرتبطة بميزة واحدة إن كان السلوك عامًا فعلًا، مدخلات ومخرجات موثّقة، أخطاء محددة. تجنب الاستيرادات الدائرية والتبعيات من واجهة إلى بيانات أو من نظام مالي إلى نظام اجتماعي.
5. **اختبارات قبل الدمج:** اختبر الوحدة والمستهلك الجديد والمستهلكين السابقين، خصوصًا الصلاحيات/حالات التعارض/الرجوع للخلف/الخصوصية. لا تفترض أن نجاح اختبارات الوحدة يثبت صحة جميع الأنظمة.
6. **حماية الأداء والكلفة:** حافظ على Firestore indexed/bounded reads وR2 exact paths أو prefix مقيد؛ لا global scans ولا polling/listeners إضافية. لا تغيّر تسلسل حذف بيانات أو مدفوعات أو اعتماد قانوني أثناء الاستخراج.
7. **التوثيق والتسليم:** في وصف PR دوّن ما أُعيد استخدامه أو سبب عدم المشاركة، والأنظمة الأخرى التي قد تستفيد، والاختبارات، وتأثير الأداء والخصوصية. حدّث بطاقات Trello الأصلية عند إنجاز المهمة. لا تعلن نشرًا قبل نجاح CI والنشر على commit المدموج.

## أمثلة تطبيقية

| نطاق العمل | جزء يمكن مشاركته | ما يجب ألا يُعمَّم دون اعتماد خاص |
| --- | --- | --- |
| البلاغات وحذف الحساب | عرض حالة الحجز/الاعتراض، audit events، read-only inventory patterns | ترخيص حذف الأدلة أو السماح بمسح الحساب |
| R2 والصور والخلفيات | تحقق مفتاح object ضمن scope، pagination صغيرة، تحقق metadata، cache helpers | مسح ملفات محادثة أو طرف آخر بمجرد غياب مرجع |
| الرسائل واليوميات | أنماط pagination، إخفاء الهوية/tombstones بعد إثبات الملكية، واجهة الأخطاء | تغيير ملكية أو حذف محادثة الطرف الآخر |
| المحفظة والهدايا والألعاب | transaction/audit utilities وتجميع التقارير | تسوية ledger أو تعويض/chargeback بلا قواعد المجال |
| الغرف والوكالات | قواعد IDs المشتركة، عرض status، تدقيق التغييرات | صلاحيات المالك أو تحويل غرف/وكالات دون مراجعة |
| Shadow Control والتطبيق | نماذج حالة موحّدة، utilities مرئية، RTL/accessibility | افتراض صلاحية من دور UI بدل تحقق backend |

**تنبيه:** `cloudflare-worker/src/account-deletion-active-holds.js` مثال على إعادة استخدام الحماية *داخل نطاق حذف الحساب*؛ ليس تصريحًا عامًا بالقراءة أو الحذف ولا يجوز استعماله مباشرة كسياسة كل الأنظمة الأخرى قبل مراجعة اختلافاتها.

## معيار قبول المهمة
لا تُغلق أي مهمة قبل توثيق: **المكوّن الموجود الذي فُحص؛ قرار إعادة استخدامه/استخراج المشترك/إبقائه خاصًا؛ اختبارات عدم كسر المستهلكين؛ حدود الأمن والأداء؛ الأنظمة الأخرى المستفيدة إن وجدت.** سجّل `لا يوجد مكوّن مشترك مناسب` عند انعدام التطابق، ولا تنشئ طبقات زائدة.

## ما بعد إغلاق حذف الحساب
عند إغلاق نظام حذف الحساب نهائيًا، نفّذ مراجعة مستقلة للأدوات المكتملة لإعادة استخدامها في تحسين R2 والبلاغات والرسائل والمحافظ والغرف/الوكالات ولوحة التحكم، كلٌّ بحسب عقده وصلاحياته واختباراته. **هذه ليست موافقة على تفعيل حذف أو تنظيف إنتاجي.**
